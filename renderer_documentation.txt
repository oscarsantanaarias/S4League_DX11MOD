--- CRenderer_D3D::EndScene     0x01C83CC0 ---------------------------------

  hr = device->EndScene();                          // D3D9 vtbl +0xA8 (idx 42)

  IMPORTANT: BeginScene/EndScene are FLAG COUNTED, not nested. The engine opens and
  closes them many times per frame (every render target change closes and reopens
  them). Our backend must do nothing expensive there.

--- CRenderer_D3D::ClearBuffer  0x01C83B20 ---------------------------------
  ClearBuffer(BYTE flags, BYTE r, BYTE g, BYTE b)
  if (m_bInScene) this->EndScene();                 // closes the scene before Clear
  d3dflags = (flags&1 ? D3DCLEAR_TARGET : 0)
           | (flags&2 ? D3DCLEAR_ZBUFFER : 0)
           | (flags&4 ? D3DCLEAR_STENCIL : 0);
  color = 0xFF000000 | (r<<16) | (g<<8) | b;
  hr = device->Clear(0, NULL, d3dflags, color, <z>, <stencil>);   // D3D9 vtbl +0xAC (idx 43)
  if (FAILED) Log("[ERROR] CRenderer_D3D::ClearBuffer [Clear %x]");

  NOTE: the game's bitmask is NOT the D3D9 one. 1=TARGET, 2=ZBUFFER, 4=STENCIL map
  one to one by coincidence (D3DCLEAR_TARGET=1, ZBUFFER=2, STENCIL=4), but the code
  makes it explicit. And Clear always goes with pRects=NULL: it clears the WHOLE
  render target, not the viewport.

--- IRenderer::CreateScreenTexture   0x01C80BC0 ----------------------------
  int fmt = 3;                                       // X8R8G8B8 by default
  ICapability* cap = GetCapability(GetRenderer());
  if      (cap->IsSupportedFormat(3)) fmt = 3;       // X8R8G8B8
  else if (cap->IsSupportedFormat(2)) fmt = 2;       // A8R8G8B8
  else if (cap->IsSupportedFormat(4)) fmt = 4;       // R5G6B5
  else if (cap->IsSupportedFormat(5)) fmt = 5;       // A1R5G5B5
                                                     // cap vtbl +0x3C (idx 15)
  MemTag("CoreLib::Renderer::IRenderer::CreateScreenTexture");
  this->m_pScreenTexture /* this+0x74 */ =
        textureFactory->CreateTexture_ColorTarget(
              /*bAutoMip*/ 0,
              /*fmt     */ fmt,
              /*width   */ 512,
              /*height  */ 512 );

  ==> THE SCENE TEXTURE IS A FIXED 512x512. It is NOT the size of the backbuffer.
      No mipmaps. Render target. D3DPOOL_DEFAULT.

--- CRenderer_D3D::UpdateScreenTexture   0x01C84680  (vtbl idx 34) ---------
  IDirect3DSurface9 *bb = NULL, *dst = NULL;
  hr = device->GetBackBuffer(0, 0, D3DBACKBUFFER_TYPE_MONO, &bb);   // D3D9 idx 18
  if (FAILED) { Log("[ERROR] ... UpdateScreenTexture [GetBackBuffer %x]"); return; }

  CTexture_D3D* t = Unwrap(this->m_pScreenTexture);                 // this+0x74
  hr = t->GetSurface(0, &dst);                                      // CTexture vtbl +0x7C
  if (FAILED) { Log("[ERROR] ... UpdateScreenTexture [GetSurface]"); ... }

  hr = device->StretchRect(bb, NULL, dst, NULL, D3DTEXF_NONE);      // D3D9 idx 34
  if (FAILED) Log("[ERROR] ... UpdateScreenTexture [StretchRect %x]");

  bb->Release(); dst->Release();

  ==> It is a DOWNSCALE from the backbuffer (e.g. 1920x1080) to 512x512.
      StretchRect SCALES in D3D9. A D3D11 CopyResource does NOT. That is why the
      fullscreen-triangle blit is mandatory when the sizes differ. It is already
      implemented that way in backend_d3d11.cpp::StretchRect.

  ==> For the copy to work the destination texture MUST have an RTV (at the very
      least, our StretchRect needs one to blit into). Since the game creates it with
      D3DUSAGE_RENDERTARGET, honouring that flag and giving it BIND_RENDER_TARGET is
      enough. Otherwise the copy is silently lost and the scene texture keeps the OLD
      frame -> the reflective floor shows whatever was on screen before.

--- Who consumes the screen texture -----------------------------------------
  The .fx files sample it as SceneMapSampler with tex2Dproj(...). The water,
  reflection, refraction and haze shaders are its main clients. That is why the
  failure looks like "the floor reflects something else".

>>> DIRECT CONSEQUENCE FOR NativeEngine <<<
The engine saves and restores render targets with a STACK, and what it pushes is
EXACTLY what GetRenderTarget(0) returns. If our GetRenderTarget always returns the
backbuffer (instead of the CURRENT target), then:
   Push(A)  -> pushes the backbuffer, sets A        [ok by accident]
   Push(B)  -> pushes the backbuffer AGAIN, sets B  [WRONG: it should push A]
   Pop()    -> restores the backbuffer              [WRONG: it should restore A]
so everything the game draws after the inner Pop goes to the SCREEN instead of to
target A, and A is left half filled / with stale content.
Expected symptoms: reflections with the wrong content, effects that look like a flat
square, stripes that appear and disappear depending on the camera.
=> GetRenderTarget(0) MUST return the surface of the current target.
The same applies to GetDepthStencilSurface.

11. REAL ORDER OF A FRAME (reconstructed)
================================================================================
  ClearBuffer(...)                    -> EndScene if needed + device->Clear
  BeginScene()
     ... scene geometry ...
     for every effect that needs an auxiliary target:
        rtMgr->PushRenderTarget(rt)   -> EndScene, GetRenderTarget(0), push,
                                         SetRenderTarget(0, rt), BeginScene
        ... draws into rt ...
        rtMgr->PopRenderTarget()      -> EndScene, pop, SetRenderTarget(0, prev),
                                         BeginScene
     UpdateScreenTexture()            -> GetBackBuffer + StretchRect to 512x512
     ... passes that sample SceneMap (water, reflection, refraction, haze) ...
  EndScene()
  UpdateScreen(0,0,0,0)               -> device->Present(NULL, NULL, hWnd, NULL)

14. FIXED-FUNCTION TEXTURE PIPELINE  (CTextureState_D3D)
================================================================================
This is what broke the flat sprites, the grey rectangles in Room Setting and the
charge bar. The engine does NOT use .fx for everything: whatever has no pixel shader
is resolved with the D3D9 texture stage states.

CTextureState_D3D vtable = 0x024074A8 (20 methods, 0x01D8EC90 .. 0x01D8EB70)

--- CTextureState_D3D::Apply  0x01D8E0C0 ---------------------------------------
  Uploads the whole stage to the device:
    dev->SetTextureStageState(stage, D3DTSS_COLOROP,   MapOp (m_colorOp))
    dev->SetTextureStageState(stage, D3DTSS_COLORARG1, MapArg(m_colorArg1))
    dev->SetTextureStageState(stage, D3DTSS_COLORARG2, MapArg(m_colorArg2))
    dev->SetTextureStageState(stage, D3DTSS_ALPHAOP,   MapOp (m_alphaOp))
    dev->SetTextureStageState(stage, D3DTSS_ALPHAARG1, MapArg(m_alphaArg1))
    dev->SetTextureStageState(stage, D3DTSS_ALPHAARG2, MapArg(m_alphaArg2))
    dev->SetSamplerState(stage, D3DSAMP_MINFILTER/MAGFILTER/MIPFILTER, MapFilter(..))
    dev->SetSamplerState(stage, D3DSAMP_ADDRESSU/V/W,                  MapAddr(..))
  Individual setters: 0x01D8E570 (COLOROP), 0x01D8E5E0 (COLORARG1/2),
  0x01D8E7E0 (ALPHAOP), 0x01D8E850 (ALPHAARG1/2),
  0x01D8EA50 (MIN/MAG/MIPFILTER), 0x01D8EB70 (ADDRESSU/V/W).
  All of them do "if it did not change, do not send it" (compared against a cached
  value).

--- Internal enum -> D3D9 translators (each one a one-line LUT) -----------------
  0x01D8ECF0  MapTexOp    -> table 0x0257001C
  0x01D8ECD0  MapTexArg   -> table 0x02570040
  0x01D8ECE0  MapFilter   -> table 0x02570008
  0x01D8ECC0  MapAddress  -> table 0x02570014
  0x01D8FE50  MapFillMode -> table 0x02570050
  0x01D8FE40  MapCullMode -> table 0x02570058

  TEXOP  @0x0257001C: 1 2 3 4 5 7 8 9 10 0
     idx 0->D3DTOP_DISABLE(1)      idx 1->SELECTARG1(2)   idx 2->SELECTARG2(3)
     idx 3->MODULATE(4)            idx 4->MODULATE2X(5)   idx 5->ADD(7)
     idx 6->ADDSIGNED(8)           idx 7->ADDSIGNED2X(9)  idx 8->SUBTRACT(10)
     ==> the engine uses ONLY these 9 operations. No DOTPRODUCT3, no LERP, no
         BLEND*ALPHA, no MULTIPLYADD.

  TEXARG @0x02570040: 0 1 2 3
     D3DTA_DIFFUSE(0), D3DTA_CURRENT(1), D3DTA_TEXTURE(2), D3DTA_TFACTOR(3)
     ==> only 4 arguments, and NEVER with the D3DTA_COMPLEMENT (0x10) or
         D3DTA_ALPHAREPLICATE (0x20) modifiers.

  FILTER @0x02570008: 0 1 2 1 3 1 2 3
     0->NONE 1->POINT 2->LINEAR 3->POINT 4->ANISO 5->POINT 6->LINEAR 7->ANISO

  ADDRESS@0x02570014: 1 3 1 2 3 4
     0->WRAP 1->CLAMP 2->WRAP 3->MIRROR 4->CLAMP 5->BORDER
     ==> the engine DOES ask for CLAMP. Forcing WRAP everywhere produces stripes.

  FILLMODE @0x02570050: 0->D3DFILL_WIREFRAME(2) 1->D3DFILL_SOLID(3)
  CULLMODE @0x02570058: 0->NONE(1) 1->CW(2) 2->CCW(3) 3->NONE(1)

>>> CONSEQUENCE <<< A D3D11 backend has no fixed-function pipeline. The stage cascade
has to be implemented in the pixel shader: per stage, pick the two arguments according
to COLORARG1/2 and apply COLOROP; the same for alpha; and D3DTOP_DISABLE cuts the
cascade. Four stages are enough. Without this everything comes out as a fixed
MODULATE(texture, diffuse).

16. HOW TEXTURES ARE BOUND
================================================================================
Only 8 functions in the whole exe call IDirect3DDevice9::SetTexture. Three of them
are in the vtable of the renderer:

--- CRenderer_D3D::SetTexture  0x01C84020  (vtbl idx 42) -----------------------
  SetTexture(stage, ITexture* tex)
  if (this->m_texCache[stage] /* this+0x6A8 + stage*4 */ == tex) return;  // cache
  this->m_texCache[stage] = tex;
  if (tex) { if (this->m_bTextureEnable /* this+0x86 */) tex->Bind(stage); }
  else     { if (this->m_bTextureEnable) dev->SetTexture(stage, NULL); }

--- CRenderer_D3D::ClearTexture     0x01C840B0 (idx 43) ------------------------
  if the cache of the stage is not null: cache=null and dev->SetTexture(stage, NULL)

--- CRenderer_D3D::ClearAllTextures 0x01C84110 (idx 44) -----------------------
  for (i = 0; i < 8; i++) { cache[i] = NULL; dev->SetTexture(i, NULL); }
  ==> the engine reasons about 8 stages.

--- CTexture_D3D::Bind  0x01DE5960 --------------------------------------------
  dev->SetTexture(stage, this->m_pD3DTex /* this+0x60 */);

  m_bTextureEnable (renderer+0x86) is set to 1 exactly once, in Init (0x01C80CF0),
  and never cleared.

17. PIXELSHADER = NULL IN THE .fx FILES  (projected shadows)
================================================================================
effect_007.fx declares THREE techniques and all three have PixelShader = null:
    Technique_TextureNoise         VS_TextureNoise
    Technique_ProjectiveShadow     VS_ProjectiveShadow
    Technique_ProjectiveShadowCast VS_ProjectiveShadowCast

In D3D9 PixelShader = null does NOT mean "do not draw": it means the pixel is
resolved by the FIXED-FUNCTION pipeline (the texture stages of section 14) with the
vertex shader of the effect. The VS are:
    VS_ProjectiveShadow:     pos = mul(InPosition, g_matWVP)
                             color = InDiffuseColor ; uv = InDiffuseMapUV
    VS_ProjectiveShadowCast: pos = mul(InPosition, g_matWVP)
                             uv  = mul(InPosition, g_matTexture).xy   <- projective texgen
    VS_TextureNoise:         uv  = mul(InDiffuseMapUV, (float3x3)g_matTexture).xy

==> A backend that requires VS+PS will mark these passes as "not compilable" and skip
    them. The correct thing is: the VS of the effect + a fixed-function pixel shader.

21. FOG: REAL VALUES, WHERE THEY COME FROM AND HOW TO IMPLEMENT IT
================================================================================
Fog is NOT hardcoded: it comes from the map's .ini. From a map bginfo file:

  [RENDERER]
  CullDist=20000
  FogMinDist=2000
  FogMaxDist=9900
  FogColorR=0.2   FogColorG=0.2   FogColorB=0.3
  ShadowColorR/G/B=0.0
  LightColorR/G/B=1    LightIntensity=100000
  InGameLightPos=(0, 3000, -5539.826)
  LobbyLightPos=(-3051, 12433, 6307)
  ShadeMapTexture=Resources/Image/nightlight01.tga

The names FOG_MINDIST / FOG_MAXDIST / FOG_R / FOG_G / FOG_B live at
0x01F37F30..0x01F37F58, and CFogPropertyCommand@Game@@ is what applies them.

VERIFIED AT RUNTIME (SetRenderState log): the engine DOES send them to the device.
  D3DRS_FOGTABLEMODE = 3           -> D3DFOG_LINEAR (PER PIXEL fog)
  D3DRS_FOGSTART = 0x44FA0000      -> 2000.0  (matches FogMinDist=2000)
  D3DRS_FOGEND   = 0x466A6000      -> 15000.0 (varies; 0x47435000 = 50000.0)
  D3DRS_FOGCOLOR = 0xFF338CFF      -> (51,140,255) sky blue
                   0xFF123375      -> (18,51,117) dark blue
  D3DRS_FOGENABLE toggles 0/1 PER OBJECT

  IMPORTANT: the startup values (start=0, end=9984, WHITE colour) are DEFAULTS, not
  the in-match ones. They have to be measured inside the map. With the default range
  the blend at 500 units is 5%: invisible.

HOW TO IMPLEMENT IT IN D3D11
D3D9 applies fog in a FIXED unit AFTER the pixel shader. D3D11 has no such thing and
the game's .fx files do not implement it (zero mentions of fog in the 63KB of the
world shader), so it has to be injected into the pixel shader.

FAILED ATTEMPT (do not repeat): reading `In.Position.w` inside the PS. The input
structs have no member called Position, so the wrapper does not compile
("error X3018: invalid subscript 'Position'"). And worse: the fog wrapper shared a
function with the alpha test one, so when the fallback kicked in those passes were
left without alpha test too and the UI broke.
  => Lesson: each wrapper needs its OWN fallback level.
     Correct chain: fog -> alpha test only -> original entry.

ALSO FAILS: adding our own `float4 neVP : SV_Position` parameter. Under backwards
compatibility the POSITION semantic the struct already carries maps to SV_Position,
and D3DCompile rejects the duplicate ("X4574: Duplicate system value semantic").

WHAT WORKS: find whichever member of the input struct carries the POSITION semantic
and read its w. In a pixel shader that w is 1/w, so the view depth is its reciprocal:

  float4 <entry>_NEFOG(<Struct> In) : COLOR {
      float4 c = <entry>_NEAT(In);
      if (g_NE_Fog.z > 0.5) {
          float d = 1.0 / max(In.<posMember>.w, 1e-8);
          float f = saturate((g_NE_Fog.y - d) / max(g_NE_Fog.y - g_NE_Fog.x, 0.001));
          c.rgb = lerp(g_NE_FogColor.rgb, c.rgb, f);
      }
      return c;
  }

The fog constants must NOT live in $Globals: the effect's cbuffer is uploaded once per
BeginPass, and the game toggles FOGENABLE per object, so reading it there gives the
wrong answer for most draws. They ride their own cbuffer at b1 which the backend
refills on every draw with the real per-object value. The UI draws with fog off, so
the wrapper is inert for it.

22. WHY A WHITE SQUARE SHOWED UP ON THE RAILGUN / DAGGER / WALL JUMP
================================================================================
The shader of that effect (dump 0x023F8288) does ONE thing:

    float4 FinalColor = tex2Dproj( SceneMapSampler, ... );
    return FinalColor;

It has no colour of its own and no diffuse texture: the only thing it paints is the
distorted SCENE TEXTURE (it derives a normal from the luminance gradient and offsets
the coordinates). Its technique also declares `AlphaBlendEnable = false`, i.e. the quad
is written OPAQUE on purpose; in the original you cannot tell, because what it paints is
almost identical to what is behind it.

Our fallback for a texture that does not resolve was WHITE (the neutral element of a
multiplication). But here nothing is multiplied, it is returned as-is: neutral white in
a shader that only returns that texture = OPAQUE WHITE SQUARE.

Fix: we do have the scene texture (the 512x512 one that UpdateScreenTexture fills,
section 4). The backend remembers its SRV when it sees the StretchRect whose
destination is 512x512, and any sampler whose name contains Scene / Screen / Refraction
gets it instead of the white one.

--- 22.b THE SAME SYMPTOM IS MAP DEPENDENT ------------------------------------
The white square on the basic (non-skin) Mind Shock / Mind Heal and on the railgun
charge is NOT constant across maps. On Station 2 the railgun charge renders correctly
(radial arc gauge plus glow); on other maps the very same weapon gives the white square.

Maps where the effects FAIL (white square), confirmed in game so far:
    Station 1, Station 2, Wonderland, Ice Square, Neden 3
There are more; they simply have not been verified yet. That is the list of what has
actually been seen failing, not the complete set. On other maps the same weapon renders
correctly. Diffing the bginfo [RENDERER] block of these against a map where it works is
the cheapest next step.

That rules the weapon out: the effect is the same asset either way. What changes between
maps is the environment the effect samples from, which is exactly what this section is
about:
  - the contents of the scene / refraction texture at the moment the effect draws,
  - the `[RENDERER]` block of the map's bginfo (fog range and colour, shademap texture,
    light position — section 21),
  - which post-process passes the map runs, and therefore what device state is left
    around the effect's draw.
So the thing to compare is not two weapons, it is two maps: on a map where it works
against a map where it does not, which SRV lands on the scene sampler and which render
states the surrounding passes left behind.

22.c WHY IT IS MAP DEPENDENT: THE SCENE TEXTURE IS ONLY REFRESHED BY THE
     GLOW / HAZE / FULLSCENE PASSES, AND THOSE ARE PER MAP
================================================================================
Reversed in IDA. The chain, end to end:

--- The shader dispatcher -----------------------------------------------------
CShaderMgr_CreateShaderByType  0x01CB6DD0   switch on a shader type id:
    1 Shader (world, VS20PS20 -> VS11PS11 -> VS11 fallback chain)
    2 Glow            3 FullSceneGlow      4 FullSceneBlur
    5 Haze            6 Haze2              7 Refraction   <<< the weapon effects
    8 Water (gated by two capability checks)              9 Effect_VS11
CShaderMgr_GetOrCreateShader 0x01CE7880 caches them in renderer+8+type*4.
CGame_PreloadShaders 0x01321500 preloads 1,3,4,6,7,8,9 -- NOT 2 (Glow) and NOT
5 (Haze): those two are created lazily, the first time a map actually needs them.

--- An effect opts into the scene texture BY NAME ------------------------------
CNodeLoader_ApplyFullSceneRT_A 0x01264900 (and _B 0x01264F80) do a substring
search for the literal "fullscenerendertarget" (0x01F3E848 / 0x01F3E904) in the
node's name string, exactly like the render state tokens of section 24. If the
name carries it, CNodeLoader_MarkFullSceneRTChildren 0x01264E30 walks the node's
children and flags every one of the matching class.
  ==> Whether an effect needs the scene texture is data, written into the .scn
      node name. It is not a property of the shader.

--- But the texture is only refreshed inside the glow/haze passes -------------
CRenderer_D3D_UpdateScreenTexture  0x01C84680  = CRenderer_D3D vtable +0x88
CRenderer_D3D_GetScreenTexture     0x01C822C0  = the next slot, +0x8C
CRenderer_UpdateScreenTextureIfAny 0x01CE7A60  = if (renderer+0x30) call its +0x2C

CRenderScene_RenderGlowPass 0x01CE2E70 (type 2) and CRenderScene_RenderHazePass
0x01CE31C0 (type 5) have the same shape, and they call
CRenderer_UpdateScreenTextureIfAny twice around EVERY object they draw. Both open
with the same guard:

    if (list_at(renderer + 0x194) is empty || list_at(renderer + 0x198) is empty
        || global_toggle() == 0)  return;         // glow
    if (list_at(renderer + 0x19C) is empty || list_at(renderer + 0x1A0) is empty
        || global_toggle() == 0)  return;         // haze

>>> THAT IS THE WHOLE BUG. A map with no glow and no haze geometry has those
    lists empty, both passes return immediately, and NOTHING calls
    UpdateScreenTexture that frame. The scene texture is then never refreshed.
    The refraction shader of section 22 paints nothing but that texture, so on
    such a map it samples a stale or never-filled surface. Our backend, which
    remembers the SRV from the StretchRect into the 512x512 target, has nothing
    to hand it and falls back to white -> the opaque white square.

    It matches the evidence: the maps where the effects render correctly
    (Station 1, Station 2, Wonderland, Ice Square, Neden 3) are all heavy on
    glowing neon geometry, i.e. exactly the maps whose glow list is not empty.

--- And the fullscene blur weights are per-map too ------------------------------
CBgInfo_ParseRendererSection 0x011948A0 reads, in this order, into the map's
render settings object:
    CullDist                    -> +0x6C
    FullSceneGlowColorRev       -> +0x70
    FullSceneGlowOrgColorRev    -> +0x74
    FullSceneGlowPeriColorRev   -> +0x78
    FogMinDist                  -> +0x64
    FogMaxDist                  -> +0x68
    FogColorR/G/B, ShadowColor*, LightColor*, light positions, ShadeMapTexture

CMapRenderSettings_Apply 0x011A2A10 then publishes the three glow weights to
globals when the map loads:
    g_FullSceneGlowColorRev      0x0256F790
    g_FullSceneGlowOrgColorRev   0x0256F794
    g_FullSceneGlowPeriColorRev  0x0256F798

and CFullSceneBlurShader_Init 0x01CBD8D0 / _BindSceneTexture 0x01CBDA00 feed them
to the shader as g_fColorRev / g_fOrgColorRev / g_fPeriColorRev -- the exact three
floats of section 28 that turn the blur black when they arrive as zero.
_BindSceneTexture also binds renderer->GetScreenTexture() (+0x8C) as the blur's
g_TexDiffuseMap, which confirms the blur and the weapon effects sample the SAME
512x512 surface.

--- DIAGNOSTIC IN PLACE -------------------------------------------------------
The backend logs a [map] line: the three glow weights (in thousandths, since Log()
has no %f) and how many times the scene texture was refreshed per 120 frames. It
reads the globals directly, so it needs no hook and cannot crash the client. A map
where the effects fail should print sceneTexUpdates=0.

--- FIX, once the log confirms it ---------------------------------------------
Do not chase the engine into calling UpdateScreenTexture: it is right not to, the
map has nothing that needs it. Refresh the scene texture ourselves when something
is about to sample it and it is stale -- we already see the StretchRect, and we
already know which samplers are Scene/Screen/Refraction.

25. "THE MAP LOOKS BRIGHTER / FLATTER": THE CLUE IS DifPow, NOT THE FOG
================================================================================
World lighting formula (effect_001.fx):

    float3 L     = normalize( g_vLightPos - tmpPos );     // in the VERTEX shader
    float4 Final = DiffuseMapColor * ( g_vLightColor * ( In.DifPow + 0.5 ) );

  variants: ... * g_TexFactor,  ... + SpecularMapColor * In.SpePower,
            ... * ( LightMapColor * 2 ),  ... * ( g_vLightColor * ShadeColor * 2 )

In.DifPow is the diffuse term (N.L) computed by the VS. The effective range of the
multiplier is 0.5 .. 1.5.

  ==> If DifPow comes out SATURATED at 1 everywhere, the whole map sits at 1.5x with NO
      variation: brighter and flat. It is not "more light", it is that the contrast
      between what is lit and what is not has been lost.

RULED OUT WITH EVIDENCE: g_Contrast / g_Saturation. The log shows them unbound (=N), but:
  - g_Contrast = 0 cancels its term: it is neutral.
  - g_Saturation = 0 would give a BLACK AND WHITE image, and that does not happen.
  - the active techniques are PS_DiffuseMap_Light0 / _Light1, NOT the
    _ContrastSaturation variants.
So those two uniforms are not the cause.

SUSPECT: the vertex NORMAL. If InNormal does not reach the VS correctly, N.L is constant
and DifPow is fixed. World geometry goes through SetVertexDeclaration (the DIP ->
BuildInputLayout path from the declaration, not from the FVF).

NEXT CHECK (one pass, no guessing):
 1. Log the D3DVERTEXELEMENT9 that arrives in SetVertexDeclaration for the world draws
    and confirm there is a D3DDECLUSAGE_NORMAL with the right type and offset, and that
    BuildInputLayout maps it to "NORMAL".
 2. Compare the g_vLightPos / g_vLightColor the shader receives against the [RENDERER]
    block of the map's bginfo (LightColor=(1,1,1), LightIntensity=100000,
    InGameLightPos=(0,3000,-5539.826)). Watch the SCALE of the intensity.
 3. If the normal is right and the light is right, look at how the VS computes DifPow
    (it may depend on a world/normal matrix we are not passing the same way).

  2. `In.Position.w` from the struct                -> COMPILES but the value is not the

Next to try, in this order:
  a) pass the depth from the VERTEX shader in a spare TEXCOORD; this means wrapping the
     VS too, but it is the only thing that guarantees the right value.
  b) reconstruct it from the depth buffer in a separate pass.

Nothing is broken in the meantime: the fallback chain (fog -> alpha test only ->

27. S4'S LIGHTING IS A SHADEMAP (a texture lookup), NOT A FORMULA
================================================================================
Shader 0x023E4198 (VS_DiffuseMap_ShadeMap_Light1), with PixelShader = null:

    float3 tmpNormal   = normalize( mul( InNormal, (float3x3)g_matWorld ) );
    float3 L           = normalize( g_vLightPos - tmpPos );
    Out.ShadeMapUV     = 0.5 * dot( tmpNormal, L ) + 0.5;

The diffuse term N.L is NOT used as a number: it is remapped to 0..1 and used as a
TEXTURE COORDINATE. The pixel is resolved by the FIXED-FUNCTION pipeline (section 14)
sampling the ShadeMap with that UV. It is toon-style shading: the light ramp lives in a
texture.

  The map declares it in its .ini:  ShadeMapTexture=Resources/Image/nightlight01.tga

>>> LIKELY CAUSE OF THE "FLAT AND BRIGHTER MAP" <<<
Our log was already reporting:
    [fx] texture NOT resolved: sampler=ShadeMapSampler tex=g_TexShadeMap slot=1
If the ShadeMap does not resolve, the fallback gives a UNIFORM 0.5 grey. A constant
ShadeMap means flat, even lighting across the whole map, with no contrast between what
is lit and what is not. That matches the symptom exactly.

NOTE: this technique has PixelShader = null, so it goes through OUR fixed-function
pixel shader, which takes its textures from d->tex[stage] (device SetTexture) and NOT
from the effect's texParams. Which of the two routes nightlight01.tga arrives by (or
should arrive by) has to be verified.

STEPS:
 1. Check whether nightlight01.tga is loaded at all (look for it in the CreateTexture
    log).
 2. Check what sits in d->tex[1] during these draws (the ShadeMap goes to slot 1).
 3. If it arrives by neither route, the problem is loading the map's resource, not
    binding it.

28. THE POST-PROCESSES, ONE BY ONE
================================================================================
0x023E4198  ShadeMap (see section 27). PixelShader = null.
            Out.ShadeMapUV = 0.5 * dot(N, L) + 0.5  -> the LIGHT is a texture.

0x023E26B8  TextureNoise + ProjectiveShadow + ProjectiveShadowCast.
            All THREE with PixelShader = null (section 17).

0x023F9870  Only offsets the UV (InDiffuseMapUV + g_TexCoordOffset).
            PixelShader = null: another pass resolved by the fixed function.

0x023E4198 / 0x023F7B50  Heat distortion. The 0x023F7B50 one uses tex2D (not tex2Dproj)
            and ends with FinalColor.a = 1: OPAQUE ON PURPOSE. Just like the one in
            section 22, the only thing it paints is the distorted scene texture, so if
            that texture does not resolve the whole quad shows up in the fallback
            colour.

0x023E3A28  8-tap blur: sums 8 samples at +-0.005 and multiplies by 0.2.
0x023E33D8  5-tap blur with weights g_fOrgColorRev / g_fPeriColorRev and a final
            multiplier g_fColorRev. If those floats do not arrive, the result is BLACK
            (everything gets multiplied by zero).
0x023E2C38  Radial motion blur: the offsets come from Out.Position in the VS, and
            FinalColor.a = tex2D(BlurMapSampler, uv).a * g_BlurFactor.
            The ALPHA comes from the BlurMap: if that texture falls back to WHITE, alpha
            is 1 and the blur covers the screen. That is why the "Blur"/"Mask" fallback
            has to be BLACK (alpha 0), as it already is.

0x023F9F18  Refraction (water): tex2Dproj(RefractionMapSampler, ...) mixed with the
            diffuse by g_DiffuseColorWeight, and FinalColor.a fixed at 0.5.

>>> GENERAL PATTERN <<<
Almost all of these passes depend on ONE screen texture (SceneMap / RefractionMap /
BlurMap) and on weight floats. When the texture does not resolve or the float arrives as
0, they do not degrade gracefully: they paint a flat rectangle (white, black, or the
fallback colour). That is why the "square" symptoms always show up in this family and
never in ordinary geometry.

>>> AND THEY ALL DECLARE THEIR RENDER STATES IN THE PASS <<<
   FogEnable = false        (0x023F8288 x5, 0x023F9F18 x4)
   AlphaBlendEnable = false (0x023F8288 x5)
This is what fixed the railgun/dagger square, and it is also what keeps fog from being
applied where the .fx disables it. Reminder for whoever touches the parser: the .fx
arrives with no line breaks, so the parser has to be scoped to the pass block or it
chews through the letters (that happened once).

--- Technique names of the world shader ---------------------------------------
The file carries the full list of variants, which confirms the combination matrix of the
63KB shader:
  Technique_DiffuseMap[_SpecularMap][_ShadeMap][_LightN][_Rigid|_Skinned]
Every combination is its own technique. Rigid vs Skinned decides whether the VS applies
g_matBone; LightN picks how many lights; ShadeMap uses the texture lookup of section 27;
SpecularMap adds the specular term.

--- 29.b FULL TECHNIQUE MATRIX OF THE WORLD SHADER ----------------------------
Axes that combine (block 0x0240C0xx..0x0240CCxx):
  base       DiffuseMap                (always)
  bump       [_BumpMap]                uses InTangentS
  static lt  [_LightMap]               BAKED lighting: Final = Dif*(LightMap*2)
  dynamic lt [_ShadeMap]               texture lookup: uv = 0.5*dot(N,L)+0.5
  specular   [_SpecularMap]            adds SpecularMapColor * SpePower
  light count[_Light0 | _Light1]
  skinning   [_Rigid | _Skinned]       Skinned applies g_matBone[48]
  quality    [_Low]                    reduced variant
Example of the extreme: Technique_DiffuseMap_BumpMap_SpecularMap_ShadeMap_Light1_Skinned_Low

  NOTE: LightMap and ShadeMap are DIFFERENT THINGS and both are called "light":
    LightMap  = per-surface baked texture with its own UVs (Final = Dif * map*2)
    ShadeMap  = light ramp indexed by the diffuse term (section 27)
  A wrong fallback in either one flattens the lighting.

================================================================================
30. THE WORLD SHADER, IN FULL (effect_001.fx, 63KB)
================================================================================

--- 30.a STRUCTURE: 4 PASSES PER TECHNIQUE, AND THEY ARE VARIANTS --------------
EVERY technique declares 4 passes with the SAME vertex shader and a different pixel one:
    p0  <base>
    p1  <base>_TextureFactor
    p2  <base>_ContrastSaturation
    p3  <base>_TextureFactor_ContrastSaturation
They are NOT layers drawn on top of each other: they are VARIANTS and the engine PICKS
one. Our log always shows "BeginPass tech=N pass=1", i.e. the TextureFactor one. If all
4 were ever drawn it would be 4x the overdraw.
  => Begin() must report the count, but the engine calls BeginPass(k) with the one it
     wants. Watch for this if things are ever seen running 4x slower.

--- 30.b UNIFORMS AND SAMPLERS ------------------------------------------------
  int   g_SpecularShiness = 16;      float g_BumpDepth = 0.75;   <- WITH a default
  float g_Contrast; float g_Saturation;                          <- NO default
  float3 g_SaturationConst = float3(0.2126, 0.7152, 0.0722);
  matrices: g_matBone[48], g_matWVP, g_matWorld, g_matViewProj
  vectors:  g_TexFactor, g_vEyePos, g_vLightPos, g_vLightColor
  samplers: Diffuse/LightMap/BumpMap/SpecularMap = WRAP
            ShadeMapSampler = CLAMP    <- the ramp must NOT repeat

--- 30.c THE LIGHT RAMP IS INDEXED BY A SCALAR --------------------------------
    float4 ShadeColor = tex2D( ShadeMapSampler, In.DifPow );
In.DifPow is a FLOAT, not a float2. HLSL expands it to float2(DifPow, DifPow): it reads
the DIAGONAL of the texture. That is why the sampler asks for CLAMP: DifPow can leave
0..1 and with WRAP the ramp would wrap around.
    Out.DifPow = 0.5 * dot( tmpNormal, L ) + 0.5      (in the VS)
With bump, the index comes from the bump in tangent space:
    ShadeMapUV = g_BumpDepth * dot( BumpMapColor, In.L ) + 0.5

--- 30.d THE THREE LIGHTING FORMULAS ------------------------------------------
  LightMap  (baked static):    Final = Diffuse * (LightMapColor * 2)
  Light1    (direct diffuse):  Final = Diffuse * (g_vLightColor * (DifPow+0.5))
  ShadeMap  (toon ramp):       Final = Diffuse * (g_vLightColor * ShadeColor * 2)
  Light0    (unlit):           Final = Diffuse
  + optional specular:         Final += SpecularMapColor * SpePower
  + optional TextureFactor:    Final *= g_TexFactor   (and alpha *= g_TexFactor.a)
  In ALL of them: Final.a = DiffuseMapColor.a

  ContrastSaturation (only in p2/p3):
    Final.rgb = Final.rgb - g_Contrast*(Final.rgb-1)*Final.rgb*(Final.rgb-2);
    Final.rgb = saturate( lerp( Lum.xxx, Final.rgb, g_Saturation ) );
  g_Contrast=0 is NEUTRAL, but g_Saturation=0 gives GREY. Since the game is not black
  and white, either those passes do not run or the engine does send g_Saturation.

--- 30.e VERTEX SHADERS: WHERE EACH THING IS COMPUTED -------------------------
  Rigid:    tmpPos = mul(InPosition, g_matWorld)
            tmpNormal = normalize( mul(InNormal, (float3x3)g_matWorld) )
  Skinned:  tmpPos and tmpNormal accumulate through g_matBone[InBoneIndex.xyzw] weighted
            by InBoneWeight, then mul(.., g_matViewProj)
            NOTE: the normal uses mul(float4(InNormal,1), (float3x3)matBone)
  Bump:     matTBN = float3x3( InTangentS, cross(InTangentS, tmpNormal), tmpNormal )
            and the light is passed to the PS in tangent space:
            Out.L = normalize(mul(matTBN, L))
  Specular: H = normalize(L + V) with V = normalize(g_vEyePos - tmpPos)
            SpePower = pow( max(dot(tmpNormal, H), 0), g_SpecularShiness )
  _Low:     the same VS but returning the struct WITHOUT bump (falls back to scalar
            DifPow)

>>> IMPLICATION FOR THE FLAT LIGHTING PROBLEM <<<
The chain is: InNormal -> tmpNormal (needs the right g_matWorld or g_matBone) -> DifPow
-> ShadeMap UV -> colour. If ANY link fails the result is even lighting. Verify in this
order:
  1. that g_TexShadeMap resolves (our log says it does NOT: "texture NOT resolved")
  2. that InNormal reaches the VS (the NORMAL element of the input layout)
  3. that g_matWorld / g_matBone arrive with the right layout (row-major)

32. GROUND TRUTH FROM A CLEAN CLIENT (d3d9spy.dll)
================================================================================
A DLL that ONLY watches was written: it hooks the Direct3DCreate9 export of d3d9.dll
with a 5 byte JMP, patches the device vtable in place and logs. It translates nothing.
Source: spy/d3d9spy.cpp.

  IMPORTANT: patching the IAT DOES NOT WORK on this exe. The log confirmed it: "NOBODY
  called Direct3DCreate9 through the IAT". The unpacked dump resolves its imports
  through wrappers, so the calls never go through the IAT slot. The EXPORT has to be
  hooked. The prologue is the standard hotpatch one
  (8B FF 55 8B EC = mov edi,edi; push ebp; mov ebp,esp), so a 5 byte detour plus
  trampoline is straightforward, with no instruction decoding.

>>> THE SHADEMAP IS A 256x1 RAMP <<<
    [spy] SetTexture stage=1 tex=... 256x1 fmt=21     (fmt 21 = D3DFMT_A8R8G8B8)
The original client DOES bind it, through device->SetTexture(1, ...). It is a strip 256
px wide by 1 tall: the light gradient indexed by tex2D(ShadeMapSampler, DifPow)
(sections 27 and 30.c).

  ==> THAT IS WHY OUR LIGHTING COMES OUT FLAT. When g_TexShadeMap does not resolve we
      fall back to 0.5 grey, a CONSTANT value, replacing a gradient with a fixed number:
      all geometry ends up equally lit.
      The fix is NOT to change the fallback value (no number produces variation): the
      texture has to arrive.
      Stage 1 also carries 256x256 DXT1 textures (fmt 827611204), which are the
      LightMaps and others; the ShadeMap is recognisable by being 256x1.

>>> FOG: the map DOES change the values <<<

    RS 36 (FOGSTART)     = 0x447A0000 -> 1000.0     (default was 0)
    RS 37 (FOGEND)       = 0x47435000 -> 50000.0    (default was 9984)
    RS 34 (FOGCOLOR)     = 0xFF123375 -> dark blue  (default was WHITE)
    RS 28 (FOGENABLE)    toggles 0/1 per object

--- 32.b CORRECTION: the VISIBLE fog is the white 0..9984 one -------------------
There are two fog configurations across the whole trace of the clean client, and the one
that produces the thick haze seen on the graveyard map is the FIRST one, the one that
had been dismissed as "the default":

  A (the VISIBLE one):  FOGCOLOR=0xFFFFFFFF white, START=0,    END=9984
  B (nearly invisible): FOGCOLOR=0xFF123375 blue,  START=1000, END=50000

With A:  d=2000 -> 20% white,  d=5000 -> 50%,  d=9984 -> 100%.
That is exactly the gradient in the capture: near geometry sharp and the background
dissolved into white. The lavender tint comes from mixing that white with the blueish
scene, NOT from a lavender fog colour.
With B:  d=3000 -> 4% blend. Practically invisible.

  => Fog IS D3DRS_FOG and there is no need to look for it in the post-process.
     The mechanism to get working is the one in sections 21/26.
     Careful with assuming "default" means "unused": here it is the other way round.

--- 32.c WHAT THE SPY IS GOOD FOR ---------------------------------------------
